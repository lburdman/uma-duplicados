# ADR 0006 — The member number is an identity document

**Status:** accepted · **Date:** 2026-08-24

## Context

The brief: no log may contain the patient's name or identity document, and the PDFs are
to be treated as if they were not anonymized.

A "Nro. de Afiliado" is 13 digits: an 11-digit CUIL plus a 2-digit family suffix. The
CUIL contains the DNI. So the member number **is** an identity document, and treating it
as an opaque key would miss the requirement entirely.

## Decision

Redaction by design, not by discipline.

- The log sink scrubs every message and every serialized field before writing. Any run
  of 8+ digits and any formatted CUIL becomes `[REDACTED_ID]`. A future
  `logger.info('parsed', item)` that forgets to redact still cannot leak, because the
  sink itself refuses to emit the shape.
- Anything that needs to correlate across events uses `patientRef()` — a salted HMAC
  prefix, stable for the same patient, non-reversible.
- `hallazgos.json` carries `pacienteRef` alongside the CUIL. The auditor needs the CUIL
  to open the PDF and verify; the redacted reference is what appears in traces and in
  the prompt.
- The LLM gets `pacienteRef` and never the CUIL. A model provider is a third party.
- Name fragments recovered from the page are counted and discarded, never stored — see
  ADR 0002.

## Consequences

Enforced by tests rather than by review:

- The full pipeline runs at `debug` level with a capturing sink; the test fails if any
  line contains 8+ consecutive digits or a formatted CUIL.
- A test asserts the LLM prompt contains no long identifier.
- A test scans every description in `items.json` for a bare uppercase token appearing
  exactly once — the signature of a leaked name fragment.

The salt is `PII_SALT`, defaulting to a fixed development value so references are
reproducible across runs. In production it would come from a secret store, and rotating
it would change every reference — which is the correct behaviour for a pseudonym.
